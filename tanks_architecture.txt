0. RESUMEN EN 30 SEGUNDOS
-------------------------------------------------------------
Brick Tanks NO es un programa aparte: es un cuarto tipo de juego
(GAME_TYPE TANKS) que usa el mismo compilador y el mismo motor que
Tetris y Snake. Todo lo que define al juego (tanques, enemigos,
jefe, balas, muros, martillo, reglas de combate y la puntuación que
hace aparecer al jefe) esta escrito en tanks.brick, no en Python.

  tanks.brick --> compiler.py --> tanks.json --> runtime.py
  (lo escribe     (lo entiende y   (representación  (lo ejecuta,
  el programador) lo valida)       intermedia)      lo dibuja)
  tanks.bnf describe formalmente lo que el compilador acepta.

Regla de oro: si Brick Tanks funciona pero Tetris, Tetris extendido,
Snake o Snake evolucionado dejan de compilar o ejecutar, la
integración no esta terminada. Por eso todo lo nuevo es opcional y
solo se activa cuando el archivo declara GAME_TYPE TANKS.

Que hace el juego:
  - El jugador (tanque turquesa) se mueve con las flechas y dispara
    con ESPACIO dentro de una arena de 20 x 16 celdas.
  - Tres enemigos distintos (SCOUT, RAPID y HEAVY) lo persiguen y le
    disparan. Cada enemigo destruido suma puntos y es reemplazado.
  - Un martillo (REPAIR_HAMMER) recupera resistencia (HP).
  - Los muros de ladrillo se destruyen; los de acero no.
  - Al llegar a 1000 puntos (ON TARGET_SCORE 1000) aparece el
    FINAL_BOSS (300 HP, mas grande, dispara con mas daño).
  - Si el jefe llega a 0 HP: VICTORIA. Si el jugador llega a 0 HP:
    derrota (GAME OVER).

2. FLUJO DE LA INFORMACION
-------------------------------------------------------------
 1) jugar.bat llama a compiler.py con games\tanks.brick.
 2) El Lexer parte el texto en tokens (palabras en MAYUSCULAS,
    números, colores #RRGGBB, corchetes, paréntesis, dos puntos).
 3) El Parser detecta GAME_TYPE TANKS y, desde ese momento, activa
    las rutinas de Tanks (DEFINE TANK / BULLET / WALL / POWERUP y los
    eventos ON ...). Valida la sintaxis y la semántica.
 4) El compilador escribe games\tanks.json.
 5) runtime.py carga el JSON, detecta tipo_juego == 'TANKS' y
    delega en sus funciones tanks_* (no toca la logica de Tetris
    ni de Snake).
 6) Cada 150 ms se lanza el evento ON_TICK; las teclas lanzan
    ON_KEY_UP / DOWN / LEFT / RIGHT / SPACE. Cada evento es una lista
    de acciones que el runtime interpreta.

3. SINTAXIS DE TANKS.BRICK (RESUMEN)
-------------------------------------------------------------
Definiciones (DEFINE ... END):
  DEFINE TANK nombre:   TYPE (PLAYER|ENEMY|BOSS), COLOR, HP, SPEED,
                        DAMAGE, FIRE_RATE, FORM, TARGET, AI, POINTS,
                        STATE n: [matriz de 0 y 1]
  DEFINE BULLET nombre: TYPE: BULLET, COLOR, DAMAGE, SPEED, SIZE
  DEFINE WALL nombre:   COLOR, HP, DESTRUCTIBLE (ON|OFF), STATE
  DEFINE POWERUP nombre: TYPE: HAMMER, COLOR, HEAL, CHANCE, STATE

Eventos (ON ... END):
  START, TICK, KEY_UP/DOWN/LEFT/RIGHT/SPACE, COLLISION_BULLET_WALL,
  COLLISION_BULLET_ENEMY, COLLISION_BULLET_PLAYER,
  COLLISION_BULLET_BOSS, COLLISION_PLAYER_ENEMY,
  COLLISION_PLAYER_POWERUP, HAMMER_COLLECTED, DESTROY_ENEMY,
  DESTROY_BOSS, PLAYER_HIT, GAME_OVER y  ON TARGET_SCORE <puntos>.

Acciones:
  SPAWN (PLAYER | ENEMY nombre | WALL nombre | POWERUP nombre | BOSS nombre)
  MOVE (PLAYER|ENEMY|BOSS) (UP|DOWN|LEFT|RIGHT|FORWARD)
  MOVE BULLETS FORWARD        FIRE (PLAYER|ENEMIES|BOSS) USING bala
  DAMAGE (PLAYER|ENEMY|BOSS|WALL) BY (n | BULLET_DAMAGE)
  HEAL PLAYER BY (n | POWERUP_VALUE)
  INCREASE_SCORE (n | ENEMY_POINTS)      DESTROY (...)
  VICTORY      GAME_OVER      GAME_OVER IF PLAYER HP_ZERO

-------------------------------------------------------------
4. JSON QUE ESCRIBE EL COMPILADOR (claves nuevas de Tanks)
-------------------------------------------------------------
  "tanks":   { "PLAYER_TANK": {type,color,hp,speed,damage,fire_rate,
                               form,target,ai,points,estados}, ... }
  "bullets": { "PLAYER_BULLET": {type,color,damage,speed,size}, ... }
  "walls":   { "BRICK_WALL": {color,hp,destructible,estados}, ... }
  "powerups":{ "REPAIR_HAMMER": {type:"HAMMER",color,heal,chance,estados} }
  "tank_roles": { "player":"PLAYER_TANK",
                  "enemies":["SCOUT_TANK","RAPID_TANK","HEAVY_TANK"],
                  "boss":"FINAL_BOSS" }
  "target_scores": [ {"score":1000,"event":"ON_TARGET_SCORE_1000"} ]
  "events":  { "ON_START":[...], "ON_TICK":[...], "ON_KEY_SPACE":[...],
               "ON_TARGET_SCORE_1000":[{"accion":"SPAWN","objeto":"BOSS",
               "params":["FINAL_BOSS",[10,2]]}], "ON_DESTROY_BOSS":[...] }

  Estas claves solo existen en los JSON de Tanks. Los JSON de Tetris
  y Snake salen igual que antes.

5.4 INTEGRANTE 4 - LAURA CARDONA GUARIN
    Sistemas de combate, estados y jefe final
-------------------------------------------------------------
  Es la capa que convierte el movimiento y los disparos de Maickel
  en un juego con reglas: quien recibe daño, cuanto, cuando se gana
  y cuando se pierde. Se acopla al runtime mediante "ganchos"
  (ver sección 6), de modo que el núcleo de Maickel funciona solo y
  el modulo de combate lo extiende sin reescribirlo.

  a) Resistencia (HP) del jugador
     - El tanque del jugador nace con hp y max_hp tomados de
       PLAYER_TANK (100 por defecto). Cada bala enemiga o del jefe le
       resta el DAMAGE de la bala; el HP nunca baja de 0.
     - Con HP 0 se activa la derrota (ON PLAYER_HIT: GAME_OVER IF
       PLAYER HP_ZERO) y el juego muestra "Juego Terminado" con la
       puntuación final.
  b) Resistencia y comportamiento de los enemigos
     - Cada enemigo guarda su propio HP, velocidad, cadencia de
       disparo y puntos según su definición (SCOUT 30, RAPID 20,
       HEAVY 60). La bala del jugador le resta su DAMAGE; al llegar
       a 0 el enemigo se elimina, suma sus POINTS (ENEMY_POINTS) y
       se crea otro (ON DESTROY_ENEMY: SPAWN ENEMY RANDOM), de modo
       que la partida siempre tiene presión.
  c) Daño por proyectiles
     - El daño sale de la bala (BULLET_DAMAGE), no del tanque, asi
       cambiar un DAMAGE en tanks.brick cambia el juego sin tocar
       Python. Orden de resolución en cada impacto: muro, enemigo o
       jefe, jugador.
  d) Martillo (recuperación de HP)
     - Al pasar el jugador por la celda del REPAIR_HAMMER recupera
       HEAL puntos (25), sin superar su max_hp, el martillo
       desaparece y se suman 50 puntos (ON HAMMER_COLLECTED).
  e) Puntuación y progresión
     - La puntuación sube con INCREASE_SCORE y con los puntos de los
       enemigos eliminados. Es el eje de la progresión: no hay
       niveles, el avance se mide en puntos.
  f) Aparición del Final Boss
     - ON TARGET_SCORE 1000 compila al evento ON_TARGET_SCORE_1000
       y a la lista "target_scores". Cuando la puntuación alcanza
       ese valor se ejecuta una sola vez SPAWN BOSS FINAL_BOSS
       AT (10, 2). El estado continuo del juego (gancho
       tanks_actualizar_estado, llamado en cada vuelta del game loop)
       es quien compara la puntuacion con "target_scores".
  g) Jefe final con resistencia acumulativa
     - FINAL_BOSS: 300 HP, 25 de daño, mayor tamaño, color y forma
       definidos en el .brick. Cada impacto del jugador resta
       BULLET_DAMAGE a su HP (el daño se acumula entre disparos) y
       el panel lateral muestra "BOSS HP". Su bala (BOSS_BULLET) hace
       25 de daño, mas que la de los enemigos (10).
  h) Estados de victoria y derrota
     - Victoria: al llegar el HP del jefe a 0 se ejecuta ON
       DESTROY_BOSS (INCREASE_SCORE 1000 y VICTORY); el panel muestra
       "VICTORIA!" y el juego termina.
     - Derrota: el HP del jugador llega a 0 (ON PLAYER_HIT).
  i) Pruebas de integración del combate
     - Jugador recibe daño y llega a 0; enemigo muere y suma puntos;
       martillo cura sin pasar del máximo; el jefe no aparece antes de
       1000 puntos; el daño al jefe se acumula; victoria al derrotar
       al jefe; derrota al quedarse sin HP; y los cuatro juegos
       anteriores siguen funcionando.
  j) Coordinación: valores de HP, daño, puntos y TARGET_SCORE vienen
     de tanks.brick (Juan Fernando) y se leen del JSON (Geremy); el
     modulo se engancha al runtime de Maickel. También participo en
     este documento y en el video demostrativo.

6. CONTRATO ENTRE MODULOS (GANCHOS DEL RUNTIME)
-------------------------------------------------------------
El runtime base (Maickel) contiene un comportamiento mínimo de
respaldo y ofrece cinco ganchos que el modulo de combate (Laura)
implementa. Si un gancho existe, el runtime lo usa (hasattr); si no,
aplica el respaldo. Asi cada parte se puede probar por separado.

  Gancho                        Quien lo llama               Responsabilidad
  tanks_danar_jugador(dano)     impacto de bala enemiga      restar HP, derrota en 0
  tanks_danar_enemigo(e, dano)  impacto de bala del jugador  restar HP, puntos, reemplazo
  tanks_danar_boss(dano)        impacto de bala en el jefe   daño acumulativo, victoria en 0
  tanks_recoger_martillo(pu)    jugador entra en el martillo curar sin pasar de max_hp, +50
  tanks_actualizar_estado()     game_loop (cada vuelta)      comparar puntuación con
                                                             target_scores y crear al jefe

Comportamiento de respaldo ya presente en el runtime: daño directo
al jugador (HP mínimo 0, fin del juego en 0), muerte de enemigos con
puntos y reemplazo, curación con martillo (+50 puntos) y victoria al
dejar el jefe en 0 HP.

7. RETROCOMPATIBILIDAD
-------------------------------------------------------------
Compilador:
  - No se elimino ninguna regla de Tetris ni de Snake.
  - Lo nuevo solo se activa con GAME_TYPE TANKS; DEFINE TANK/BULLET/
    WALL fuera de Tanks da error semántico claro.
  - Los .brick anteriores no necesitan ninguna etiqueta nueva.
JSON:
  - tetris, tetris_remake, snake y snake_evolved no reciben las
    claves tanks, bullets, walls, tank_roles ni target_scores
    (lo verifica test_juegos_anteriores_compilan_sin_claves_de_tanks).
Runtime:
  - Cada juego tiene sus propias funciones (tetris_*, snake_*,
    tanks_*); el tipo de juego se identifica antes de ejecutar nada.
  - Las funciones originales se conservan; no hay dependencias
    externas.
Entorno: Python 2.7, Tkinter, solo librería estándar, ejecución por
jugar.bat sin cambios.

9. DECISIONES Y LIMITACIONES CONOCIDAS
-------------------------------------------------------------
  - Un solo evento ON TARGET_SCORE (un solo jefe por partida); es
    una regla del lenguaje y la valida el compilador.
  - El jefe se desplaza y colisiona en una zona de 2 x 2 celdas
    aunque su figura dibujada sea mas grande.
  - FORM, AI y TARGET se validan y quedan en el JSON; el runtime hoy
    solo usa el comportamiento AGGRESSIVE aleatorio para enemigos.
  - Los eventos de colisión del .brick (ON COLLISION_BULLET_*) estan
    soportados por el compilador y la gramática; en el runtime las
    colisiones se resuelven directamente en tanks_resolver_impacto_bala.
